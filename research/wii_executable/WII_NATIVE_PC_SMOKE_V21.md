# V21: first native Windows/Linux C++ physics host build

**2026-11-11.** This milestone creates an actual native C++17 **command-line executable** from the reconstructed Wii rigid-body source. It is a deliberately limited **physics smoke test**, **not a ported playable Need for Speed: Undercover game**, and does not link or ship the original Nintendo/EA game.

## What's new

- `CMakeLists.txt` builds `nfsuc_wii_physics` as a standalone native static library using the source-only Attrib memory bridge and the currently reconstructed rigid-body methods (integration, quaternion/matrix, begin/end-frame, sleeping, force/torque resolution, drag, transformations and Detach).
- `pc_physics_smoke.cpp` builds `nfsuc_physics_smoke`, a **real host-architecture executable** with `main()`. It allocates an entirely synthetic, bounded, big-endian 32-bit Wii memory region, fills only original object offset fields needed for the test, then advances a body through the reconstructed `OnBeginFrame` and `OnEndFrame`.
- The host calls the V18 aerodynamic drag through the V16 base virtual interface, and invokes the V20 source-backed `Detach` method. Its synthetic object deliberately has the detached flag `0x0002` **clear**: original Detach takes the verified no-op branch. This does **not** fabricate the game's owner-event callbacks.
- A CI workflow `.github/workflows/wii-native-host.yml` builds and tests this same native executable on **Windows (MSVC)** and **Linux (system compiler)**, without invoking Dolphin, downloading original game files, or relying on console toolchains. The two tests execute **2** and **4** steps, respectively.

## Prebuilt CI binaries for source-only physics testing

When the `Native Wii physics host smoke (Windows and Linux)` workflow
passes, its artifacts contain `nfsuc_physics_smoke.exe` for Windows
and `nfsuc_physics_smoke` for Linux. These **14-day CI artifacts**
are compiled exclusively from independently authored host source and
synthetic test data. They do not contain the original game executable,
commercial assets or playable game content.

Open the matching GitHub Actions run and locate the two downloadable
artifacts under the run's **Artifacts** section. Those binaries run
the console CSV smoke only, not the game. If the workflow has not yet
completed successfully, use the source/CMake instructions below instead.

## Build on Windows (Visual Studio 2022 + CMake)

~~~powershell
cmake -S research/wii_executable -B build/wii-native -DCMAKE_BUILD_TYPE=Release
cmake --build build/wii-native --config Release
ctest --test-dir build/wii-native -C Release --output-on-failure
.\build\wii-native\Release\nfsuc_physics_smoke.exe --steps 4
~~~

The built-in Visual Studio CMake generator typically creates the executable under `Release`. With Ninja, the executable is instead under `build/wii-native` (without a `Release` subfolder).

## Build on Linux (GCC/Clang + CMake)

~~~sh
cmake -S research/wii_executable -B build/wii-native -DCMAKE_BUILD_TYPE=Release
cmake --build build/wii-native --config Release
ctest --test-dir build/wii-native --output-on-failure
./build/wii-native/nfsuc_physics_smoke --steps 4
~~~

Program output is a plain-text CSV header followed by one row per synthetic frame:

~~~text
frame,position_x,position_y,position_z,velocity_x,velocity_y,velocity_z,queued_force_x,queued_force_y,queued_force_z
~~~

Each step asserts that the source-backed `OnBeginFrame` consumes the **previous** frame's queued force, that force is then cleared and regenerated by the end-frame drag callback, that the resulting aerodynamic force opposes the body's current linear velocity, and that the frame-processing flag is cleared. Nonfinite/inconsistent state returns failure rather than emitting an apparently valid trace.

### Scope and limitations

This **does establish the path from Wii PPC source reconstruction to a host-native C++ executable**, independent of console emulation. It does **not** mean the original binary is decompiled end-to-end or that its gameplay can already execute. The host uses a synthetic fixture, **no actual cars, wheels, track, input, NPCs, audio, graphics, textures, streaming, menus or original assets**. The collision pass is intentionally disabled, the primitive list is empty, and the game-level scheduler is an explicit fixed-step driver rather than the original game's complete event loop. Matrix/float operations are behaviorally approximated, not proven PPC bit-exact.

The exact CI success state for both operating systems is determined by the Actions run on the relevant head commit. Treat an in-progress/failed Windows build as unverified until fixed.

**Next engineering gate:** factor the temporary test fixture into a reusable owner-local state builder / host simulation interface; bring in original Wii runtime traces for floating-point differential tests; recover vehicle-specific steering/suspension and collision primitives. Only then can the runtime be tied to an actual world/renderer and become a prototype you can drive.
